- **CLI:** Read-only commands for the instance on a key's instance level: `catalyst usage show|breakdown`, `catalyst audit events|activities`, `catalyst jobs summary|list`, `catalyst operation runs`, `catalyst modules list` and `catalyst infrastructure show`. Each calls the existing read operation (`usage.get_summary`, `usage.breakdown.get`, `audit_events.list`, `audit_activities.list`, `instance.jobs.summary`, `instance.jobs.list`, `operations.list_runs`, `instance.modules.list`, `instance.infrastructure.get`). `audit events`, `jobs list` and `operation runs` print one page with its `nextCursor`. A key without the right is refused with the right named. See the CLI reference ("Workflows, checks and lists").
- **Personal API keys:** The instance level of a key now offers `usage.view` and `audit.view` beside `system.view`, over the whole instance only and never ticked in advance, also not for the key `catalyst setup` creates. A key that names one of them carries the new operation scope `instance:inspect`, which only the nine read operations above accept from a key; each still asks the right of its own of the key and of its owner at the moment of the call, so a right the person loses is gone from the key. A key that names `audit.view` also lists and reads another person's Operation Runs (`catalyst operation runs`, `catalyst operation show`); a key without it lists and reads only its owner's. A `system.view` key issued before this release keeps its old reach, the read-only provider check, and gains the instance reads only once it is reissued. A key still decides no approval, retries no job, and reaches no user, right, technical account, credential, spend limit or usage by named person.
- **Platform context:** `instanceActions` also lists `usage.view` and `audit.view` for a person who holds them, so the key screen offers them.
