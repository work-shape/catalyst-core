---
title: Capacity and limits
description: Size an instance using the limits enforced by the platform code.
---

For an instance serving 5,000 to 10,000 people, size against simultaneous runs, model calls, uploaded files and retained conversations. The code states limits for individual requests and workers. It does not state a supported people count or a hardware size for that population.

The tables below describe the platform packages in this repository. A capability can add its own limits. Check its implementation separately, especially for document ingestion. Defaults are the values used when the setting is omitted. MiB means 1,048,576 bytes and KiB means 1,024 bytes. Source paths are relative to the repository root.

**Fixed** means there is no release config or environment knob. Where a TypeScript constructor option exists, the table names it separately. A page size bounds one response or screen, not the number of stored records. A renewable lease detects a lost worker; it is not a maximum job duration.

See [deployment](/operate/deployment/), [release config](/configure/release-config/) and [governance](/operate/governance/) for deployment and policy details.

A data tool is an agent tool that exists as data, such as an operation of a Connection (`connection.<name>.<operation>`). It is called as an operation like every other tool, so the same policy applies: a changing data tool is refused for an agent under the default `confirm`, and it runs without a confirmation where an administrator's central setting says `allow`.

The conversation list uses the shared API paging defaults of 50 items, at most 200 per request (`listQuerySchema` in `packages/api-contract/src/shared.ts`). The sidebar asks for 30 conversations at a time (`RAIL_PAGE_SIZE` in `packages/chat-ui/src/api/rail-conversations.ts`): one request when a workspace opens, and one more each time a person scrolls to the end of the list or picks "Load more". The browser holds the pages a person has loaded until they switch workspace, so the rows held are 30 times the pages loaded, and every loaded row is on the page. While a run is active outside the open conversation, or a new conversation waits for its title, the sidebar reads its first page again every 2 seconds (`RAIL_REFRESH_INTERVAL_MS` in `packages/chat-ui/src/workspace/use-conversation-list-refresh.ts`); no request reads more than one page.

When web fetching is enabled, tool calls also use the following budgets from `webAccess.fetch` in `packages/config-schema/src/schemas.ts`. Enforcement is in `packages/web-access/src/direct-web-fetcher.ts`.

## Jobs and workers

Agent runs have their own worker and lease path when the assembly selects `agentRuntimeMode: "worker"`. `createClientInstanceApp` in `packages/client-assembly/src/app.ts` defaults to local execution in the API process, so the agent worker slot limit does not apply to that mode. Other background work uses the shared Postgres job executor. Worker slots are per process. Job kind concurrency limits apply across the instance.

## Model usage and admission

Usage safeguards are instance totals across people, API processes and workers. Titles and approval checks also consume them. Admission reserves capacity before calling the provider. These safeguards can be exceeded when a completed call uses more than its reservation; they are not provider output caps.

A config push is one `assets.sync` call: at most 2,000 items for a holder of the release right and 200 for every other caller (`ASSET_RELEASE_SYNC_MAX_ITEMS`, `ASSET_SYNC_MAX_ITEMS` in `packages/api-contract/src/assets.ts`), in a request body of at most 20 MiB (`ASSET_SYNC_BODY_MAX_BYTES`, the same file), of which one put item takes at most 2 MiB (`ASSET_SYNC_ITEM_MAX_BYTES`). All four are fixed. The body is parsed in memory before any check, so one push costs up to that much memory and blocks the process while it is parsed; the write rate limit bounds how many arrive. A push takes one lock per instance on the asset set, so pushes and saves of one instance are applied one after another, each for the time of its own items. Under the lock the statements grow with the items in steps of 500 (`ASSET_WRITE_CHUNK` in `packages/postgres-store/src/postgres-config-asset-operations.ts`), not per item: the rows of all named assets in one read, their highest revisions in one, then inserts and one update per 500 items. Measured on a local Postgres 17 with small skills: 200 updates in 7 statements and about 40 ms, 2,000 creates in 12 statements and about 200 ms, 2,000 updates in 13 statements and about 170 ms. Larger definitions add transfer time, bounded by the 20 MiB body. Before the write the lock also covers one read of the active revision ids of the instance (one row per active asset), and a full read of the asset set only when another write changed it since this one was checked. The CLI says to push in parts with `--only` at either limit. A first `catalyst config pull` reads each asset with one `assets.get`, eight at a time, so it grows with the asset count and is bounded by `rateLimits.readPerMinute` (default 6,000); later pulls read only assets whose revision changed. No total asset-count ceiling exists; that gap is listed below.

## Not yet stated

These are gaps in the platform code searched for this page, not promises of unlimited capacity.

- **Chat and runs:** a maximum queued or simultaneously active run count across the instance, a per-person daily run quota, a hard total agent run duration, an enforced generic operation timeout, a total conversation or message ceiling, and a cap on the full recent conversation list loaded by the browser. The palette's eight choices and search's 20 matches do not provide those ceilings. Provider context windows depend on the selected model; no universal context ceiling is stated here.
- **Jobs and workers:** a maximum queued job count or a shared queue admission budget across kinds. Per-kind concurrency and per-process slots limit execution, not enqueueing.
- **Model usage and admission:** a default instance call, token or spend allowance, and a platform-wide simultaneous model call ceiling. The optional safeguards are unset by default. The 16,000-token reservation does not set a provider output maximum.
- **Assets and Build:** a total asset count or byte ceiling, a ceiling on the full overview response, and revision retention. Build itself no longer reads the overview.
- **Workspaces and files:** a total instance storage budget, a total workspace or membership count, a queue length ceiling for commands or browser uploads, and one upload budget covering every attachment handler. The workspace source file budget covers that handler only.
- **Documents:** a universal ingestion page, byte or document-count cap, an extraction queue limit, and document worker concurrency, leases or retention for capability-owned processing. The platform preview worker's limits do not establish them.
- **Inbox and approvals:** a total pending request ceiling, a cap on the complete Inbox fetch, retention for all approval requests, and a concurrency ceiling for the parallel approval check calls.
- **Database:** a platform database size or row ceiling, a platform query statement timeout, a platform connection acquisition deadline or queue length cap, a connector waiter-count cap, and a usage record retention period. Usage records remain after account or workspace deletion with attribution removed. Migration lock acquisition also has no deadline (`packages/postgres-store/src/migrations.ts`).

For generic operations, `DEFAULT_OPERATION_TIMEOUT_MS` in `packages/chat-server/src/operations/operation-face.ts` declares 300,000 ms (five minutes), overridable through the TypeScript binding's `timeoutMs`. The current `packages/tool-execution/src/run-operation.ts` calls the operation without consuming that timeout. No timeout message or enforced ceiling follows from the declaration alone.

For 5,000 to 10,000 people, record the expected peak active runs, model calls per run, documents and bytes per day, asset count, and retained conversation volume before assigning hardware. Validate those workloads against the instance's actual configuration and capability packages. This page supplies code limits; it supplies no measured throughput claim.
