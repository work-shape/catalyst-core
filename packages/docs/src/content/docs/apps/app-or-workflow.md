The line between an App and a Workflow:

> An App shows data and lets the person using it do one thing at a time. Anything that is a process (several steps, a schedule, history, notifications, rules business users change) is a Workflow the App starts with a button. A live read through a Connection respects the viewer's rights. Stored data read through an App is shared with its audience.

Not in this release: the `decision` action and the `code` action. The build refuses `kind: code`; until it comes, logic that combines reads for the viewer stays in the App's browser code, and anything that is a process is still a Workflow.

## Outside data

An API that needs a key, has no CORS or is also used by a Workflow is an `http_api` Connection, called through a `connection` action ([connect a system](/configure/build/#connecting-an-outside-system)). A public API only the App calls is a host in the App's `externalHosts`. In this release such a host takes effect when the App is published: its draft and the preview cannot reach it yet.

## The order to build in

One conversation builds the Data Store, the Workflow and the App, the App last, and the agent says what it creates before it does. The App comes last because its actions name the Data Store and the Workflow. The agent tries the App's draft before anything is published, with `apps.try_action`, the same call as a click on the action's button in the draft: a `workflow` action starts a test run of the Workflow's draft, and nothing is live. It never asks the person to publish in order to try something. When the person wants it live, `apps.publish_review` says what publishing the App comes to: the App and the Workflows it calls, what is pending in each and what would refuse it. In this release each pending Workflow is published first, then the App. [Build an App](/apps/build/) says how to write each action; [Workflows](/automate/workflows/) says how a person tests and publishes one.
